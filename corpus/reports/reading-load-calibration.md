# 読解負荷レーン 校正レポート（2026-08）

`lint.py --reading-load` の6検出器を、実文書241本に当てて校正した記録。

> 使用したコーパスは筆者個人・業務アカウントの Artifact Share 文書のため、リポジトリには収載しない。
> 本レポートに載せるのは集計値と、判断を説明するために作った合成例のみで、原文の引用は含めない。

## このレーンの採否基準

`readability-sweep.md` は候補14件を検証して**実装推奨0件**と結論した。ただしその判定基準は
「AI か人間かを弁別できるか」「下手な人間の文章を当てられるか」であり、分類器としての基準だった。
文長の AI検出率 1.0% は「長い文は AI の証拠にならない」という意味であって、
「長い文は読みやすい」という意味ではない。レポート自身が総括している。

> 今回検証した14候補は、いずれも「AIらしさ」の代理指標であり「文章の読みにくさ」の
> 直接的な代理指標にはなっていない。

読解負荷レーンの目的は分類ではなく推敲なので、採否基準を
**「指摘に従って直した文が、原文より読みやすくなるか」**に置いた。本レポートはその基準での校正である。
したがって FP率・AI検出率は測っていない（測っても採否の判断材料にならない）。

## 校正で変えたこと

### 1. `too_many_ten`（読点4個以上）を `buried_list` に置き換えた

初版は「一文の読点が4個以上」を B4（読点の位置が悪い・多すぎる）として指していた。
結果は**573件・文書の62%が発火**。中身を見ると、ほぼ全件が同格の列挙だった。
読点の打ち方の問題ではなく、列挙が一文に埋もれている問題（F1）である。

そこで検出器を作り直し、**読点区切りの区画が名詞で終わる並び**を検出して F1 を指すようにした。
実装上の要点は2つ。

- 列挙の最後の項目は述語に溶ける（「A、B、C を行います」の C）ので、裸の名詞句で終わる区画は
  項目数より1つ少なく数えられる。連続する名詞句区画が (項目数-1) 個あり、そのあとに区画が続けば列挙とみなす。
- 区画の末尾が括弧グループのときは、括弧ごと遡ってから品詞を見る
  （「確認ポイント（どのアプリが前面に出るか）」を取りこぼさないため）。

### 2. `buried_list` の項目3個を長い文に限定した

作り直した直後は 670件・文書の70%が発火した。項目数別に目視すると精度がはっきり分かれた。

| 項目数 | 件数 | 目視した印象 |
|---|---|---|
| 3個 | 296 | 精度が落ちる。括弧の中だけの列挙、並列の条件節の誤認が混ざる |
| 4個以上 | 374 | ほぼ全件が真の列挙。箇条書きにすれば読みやすくなる |

項目3個のときだけ一文80字以上に限定した。結果 503件（文書の63%）。
なお meiseki の F1 は発動条件を「同格の項目が3つ以上、かつ一文が長い」としているが、
実測では3項目の帯だけ精度が落ちるため、3項目側に追加の長さ条件を課している。

### 3. `kanji_run` から固有名詞を除外した

目視すると「東京地方裁判所」「特定商取引法表示」のような固有名詞・法律用語が混じっていた。
分解できない名前であって、書き手が直せる読みにくさではない。形態素に固有名詞を含む連なりを
除外して **49件→44件**。拾いたい側（「初回課金転換率」「視覚回帰受領証」「代表状態再批評」のような
AI が作る圧縮漢語）はいずれも普通名詞だけで構成されており、除外の影響を受けない。

なお「専属的合意管轄裁判所」は全形態素が普通名詞のため残る。これは誤検知として許容する
（実際に読みにくく、指さす価値がある）。

### 4. `double_negative` から条件形を除外した

初版は73件（文書の22%）。誤検知の最大の塊が「〜ないと動かない」「〜なければ意味がない」型だった。
形の上では否定が2つあるが、日本語で必要条件を述べる標準的な言い方であり、
読み手が符号の反転を計算することはない。除外して **73件→49件**（文書の16%）。

「〜ないとは言えない」（真の litotes）は「と」の直後に「は」が来るので除外されない。
義務の定型（「〜ないといけない」「〜なければならない」「〜ざるを得ない」）は初版から除外している。

`no_chain` は件数こそ少ないが、目視した11件すべてが真の「の」連鎖だった。再現率は低く精度は高い。

## 検出器を1本削除した（2026-08 追加）

`doubled_conjunctive_ga`（接続助詞「が」の連鎖、カタログ B6）は削除した。
AI生成文書 9,889文で1件、人間執筆文書 379文で**0件**しか発火しない。

初版のレポートでは「『が』を連ねるのは人間の悪文の癖なので、人間の草稿に当てたときに効く想定で残す」
と書いたが、下記の追試で取った人間執筆側のベースラインがこれを否定した。根拠のない期待で
検出器を残すと、あとから読む人が「効くはずのもの」と誤解する。必要になれば書き直せばよい。

## 追試: 人間執筆との比較（2026-08 追加）

初回の校正はコーパスがほぼ AI 生成だったため、「人間の良文で暴発しないか」を確認できていなかった。
筆者の Zenn 記事（`zenn-content`）のうち、2024年に公開した10本を人間執筆側のサンプルとして追試した。

対象の選び方は次のとおり。リポジトリは 2024-03 の Initial commit 始まりで一括インポートの形跡がなく
（1コミットあたり最大2本の追加）、git の初出日は公開日とみなせる。2024年の16本のうち
`conform-shadcn-ui-*` の6本は同一テンプレートの複製で、同じ文が6本に転写されているため除外した。

| | 人間執筆（zenn 2024） | AI生成（artifactshare） |
|---|---|---|
| 規模 | 10本 / 379文 | 241本 / 9,889文 |
| 指摘密度 | **37件/千文** | **145件/千文** |
| 指摘0件の文書 | 5/10 (50%) | 35/241 (15%) |
| 文長 p50 / p90 | 37字 / 67字 | 44字 / 86字 |
| 90字超の文 | 1.8% | 8.3% |

密度で約4倍、90字超の割合で約4.6倍の開きがある。**人間の良文に対してレーンが暴発してはいない**ことは確認できた。

ただし解釈には注意が要る。両者は文書タイプが違う（短い技術チュートリアル vs 密度の高い仕様書・分析メモ）ので、
この差の全部を執筆者の違いに帰属させることはできない。実際、同じ zenn-content 内でも
長文の分析記事が増えた2026年は 62件/千文 まで上がっており、**指摘密度は内容の密度に連動する**。
このレーンが測っているのは「AIらしさ」でも「下手さ」でもなく、一文あたりの込み入り具合である、
という設計上の位置づけと整合する。

人間側10本の内訳は `sentence_too_long`=7 / `no_chain`=3 / `buried_list`=3 / `double_negative`=1。
`kanji_run` は0件、`doubled_conjunctive_ga` も0件だった（後者はこれを受けて削除した。上節参照）。うち3件は1本（`shadcn-admin-react-router`）に集中しており、
この記事だけ p90=96字・最長142字と他（p90 54〜80字）から外れている。結びが
「あなたの次の管理ダッシュボードの構築に役立つことを願っています」と英語直訳調で、
他記事と成立過程が異なる可能性がある。

## 既知の限界

- 括弧の**内側だけ**で完結する列挙を、外側の文の列挙として指してしまう例がある。
- 動詞連用形で並ぶ手順の列挙（「設定を読み込み、依存を解決し、初期化して」）は取れない。
  現在の `buried_list` は名詞句の並びだけを見ている。
- 人間執筆側のサンプルは10本・379文と小さい（上記の追試）。同一の書き手・同一媒体でもあり、一般化はできない。
- 「直したら読みやすくなるか」の判定は目視で、複数人での一致は取っていない。
- リンク記法を挟む列挙を `buried_list` が取り逃す。実例として
  「React Router v7 は、SSR をサポートしており、[Cloudflare Workers](...) や [Fly.io](...)、[Cloud Run](...)、[AWS ECS](...)」
  （142字）は `sentence_too_long` だけが拾い、F1 としては指せていない。
