# お手本セットの文章源 調査レポート

- 調査日: 2026-10-03
- 目的: 「目指す読みやすさの手本」になる、人間が書いた仕事の文書を集める経路を探す
- 対象の書き手: 営業・企画・人事・経理・総務・カスタマーサポート・広報・管理職など。IT エンジニアに偏らせない
- 関連: 白書・EDINET・PR TIMES の初回調査は `business-corpus-sources.md`(2026-07-12)にある。本レポートは「お手本」の観点で調べ直し、規約と取得経路を一次情報で確かめた

## 1. 結論

1. **本文をリポジトリにコミットしてよい候補は見つからなかった。** どの候補も本文の著作権は書いた会社にある。コミットするのは URL・日付・会社名・業種・質のラベルといったメタデータだけにする。これは対コーパスの運用(本文は gitignore、manifest だけコミット)と同じ形になる
2. **時期で分けられて、規模も業種の幅もあるのは EDINET の有価証券報告書だけ。** API で日付つきに取れ、閲覧期間は10年ある。2016年以降の提出分が取れるので、生成AI以前と AI 時代を同じ会社で比べられる。ただし法定開示の文体で、仕事の文書の手本としては硬い
3. **質の手がかりは、外部の評価リストを「ふるい」として重ねて作る。** 金融庁の「記述情報の開示の好事例集」、日本証券アナリスト協会の「ディスクロージャー優良企業」、日経統合報告書アワード、PR TIMES のプレスリリースアワード、第三者委員会報告書格付け委員会の格付けが使える
4. **社内向けの文書(社内報・社内ルール・議事録)の公開例は少ない。** 社内報アワードは受賞の一覧だけで、本文は公開されていない。行動規範・行動指針は多くの会社が公開しているが、条文調で手本の幅は狭い

## 2. 判定の前提

### 2.1 権利

- 規約で確かめたのは「取得してよいか」と「複製・再配布をどう扱うか」まで。手元での評価利用が法的にどう整理されるかは、このレポートでは確かめていない(未確認)
- EDINET は利用規約で掲載情報を「公共データ利用規約(第1.0版)」(PDL1.0)の条件で使えるとしている。ただし PDL1.0 には「第三者が著作権を有しているもの」は利用者の責任で許諾を得る、という条項がある。有報の本文の著作権者は提出会社(国から見て第三者)なので、本文のコミットは PDL1.0 では保証されないと判断した
- 会社のウェブサイトの文書は、各社のサイト規約による。例として花王のサイト規約は、個人的・非商業的・家庭内での利用を除き、書面の許可なく複製・転載・再利用することを認めていない

### 2.2 時期

- 生成AI以前は 2022年11月以前(ChatGPT の公開前)とする
- 法定開示や IR 資料は、前年の文章を引き継いで書くことが多いと考えられる(推測。未確認)。2022年の文書でも、それより前に書かれた文の再掲を含む。AI 時代の文書にも以前の文が残る。時期で比べるときは、同じ会社の前年版との差分を見る必要がある
- 日付が画面にない会社のページは、Internet Archive の Wayback Machine の CDX API で、2022年以前に存在したかを確かめられる。`https://web.archive.org/cdx/search/cdx?url=www.kao.com/jp/corporate/news/*&from=2021&to=2022` で、2021年のスナップショットが返ることを確かめた

### 2.3 質

- 「プロの書き手が書いた」「広報・法務・監査の確認を経た」だけでは、読みやすさの保証にならない。開示の質や話題性で選ばれた文書が、読みやすいとは限らない
- そのため、外部の評価リストは「候補を絞るふるい」として使い、最終的な採否はスキルの基準(文体憲法12箇条や lint の指標)で人が見て決める

## 4. 候補ごとの補足

### 4.1 EDINET 有価証券報告書(#1)

- 仕様書(EDINET API 仕様書 Version 2、2026年6月)で確かめたこと
  - API キーの指定は必須。キーの発行にはアカウント作成が要る
  - 書類一覧 API: `https://api.edinet-fsa.go.jp/api/v2/documents.json?date=YYYY-MM-DD&type=2&Subscription-Key=...`
  - 書類取得 API: `https://api.edinet-fsa.go.jp/api/v2/documents/{docID}?type=N&Subscription-Key=...`。type=1 は提出本文書と監査報告書(XBRL を含む ZIP)、type=5 は XBRL を CSV に変換したもの(書類一覧の「CSV 有無フラグ」が1のとき)
  - ファイル日付は「直近の財務局営業日の24時において10年を経過していない日付」を指定できる
  - 大量リクエストには 429 を返す。取得間隔を見直すよう書かれている
- キーなしで書類一覧 API を呼ぶと `401 Access denied due to invalid subscription key` が返ることを確かめた
- 業種は EDINET コードリストの「提出者業種」の列で層化できる(列名は仕様書と既存資料による。ファイルの中身は未確認)
- 記述部分の本文が type=5 の CSV に入るかは未確認。入らなければ type=1 の XBRL から TextBlock 要素を取り出す。これを最小手順の最初に確かめる
- 利用規約: https://disclosure2dl.edinet-fsa.go.jp/guide/static/disclosure/WZEK0030.html (令和7年4月25日改訂)
  - 2.2「スクレイピング等を利用して本ウェブサイトからコンテンツを機械的に取得することは禁止します。ただし、API機能を利用する場合……はこの限りではありません」
  - 3.2「短時間における大量のアクセスその他のAPI機能の運用に支障を与える行為」を禁止
- PDL1.0 の第三者の権利の条項: デジタル庁「公共データ利用規約(第1.0版)」の解説 https://www.digital.go.jp/assets/contents/node/basic_page/field_ref_resources/f7fde41d-ffca-4b2a-9b25-94b8a701a037/b44a7e0c/20240705_resources_data_outline_07.pdf

| B | PR TIMES アワードの受賞・最終審査リリース | お知らせ・発表の手本。中小企業や医療機関まで書き手の幅が出る | 2021年の受賞8本と2022年の最終審査44本で50本強(2021年の最終審査の本数は未確認)。2024年以降で数十本 |
| C | A・B のふるいで選んだ会社の IR 資料(質疑応答要旨・トップメッセージ)と、格付けの高い不祥事事案の再発防止策・お詫び | 議事要約・社内外への説明・お詫びの手本 | 数十本(手作業) |

A は量と時期の軸、B と C は文書タイプの幅を受け持つ。社内向けの文書(社内ルールの説明・社内連絡・手順書)は、どの経路でも薄い。そこは行動指針(#8)と CS の FAQ(#13)で補うか、別の手段(協力企業からの提供など)を考える必要がある。

## 6. 最初に試す最小手順

1. EDINET のアカウントを作り、API キーを発行する(多要素認証の電話番号が要る)
2. `documents.json?date=2022-06-24&type=2` を1回呼び、書類種別コード 120(有価証券報告書)と CSV 有無フラグを確かめる
3. 1社分を type=5(CSV)と type=1(XBRL)で取り、「経営方針、経営環境及び対処すべき課題等」の本文がどちらに入っているかを確かめる
4. 同じ会社の2026年6月提出分も取り、前年踏襲でどれだけ文が変わっていないかを見る
5. 好事例集の2018〜2021年度版から会社名を拾い、EDINET コードリストの提出者業種で偏りを見る
6. PR TIMES 2022年アワードの最終審査44本の URL・日付・会社名を手で一覧にする
7. 本文は gitignore 済みの場所に置き、manifest(会社名・書類 ID・URL・日付・業種・ふるいのラベル)だけをコミット対象にする。`.gitignore` に新しいディレクトリの規則を足す
8. 数本に `lint.py` と `outline.py` をかけ、手本として残すかを人が判断する。基準が決まってから本数を増やす
