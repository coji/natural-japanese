# logic:文書の中で筋が通っているかを、YAML に書き出して検査する

文書はそのまま残し、論理構造を書き出した YAML と、指摘の一覧を返す。「主張と根拠が合っているか見て」「矛盾がないか確かめて」「ロジックが弱くないか」という依頼に答えるモードで、答えはすべて文書の中にある。使うのは文書の中の事実と、文書の中の数字どうしの足し算・引き算・割合だけ。暦(曜日)、単位換算、業界の常識、別の測り方や手段の代案(「ツール側の記録は使わないのか」「他部門の集計はあるのか」)は文書の外のもので、somosomo の仕事になる。測り方については、文書にある測り方の根拠を問う。

文書が AI の書いたものか人の書いたものかで、検査の仕方は変えない。

## 手順

1. 文書を読み、段落・見出し・箇条書きの1項目・表の1行を、それぞれ1つの単位として行番号で数える。見出しは、その節の主張として扱う
2. 文書の性格を1行で決める。何かを決めてもらう文書(提案・稟議・企画)か、事実を報告する文書(報告・議事録)か、経緯を語る文書(振り返り・記事)か。主結論が置かれていない文書(振り返り・経緯の記述)では、「紹介する」「振り返る」のような文書の目的を主結論の欄に書き、原因・判断・評価を述べている節を検査の中心にする
3. 論理構造を下の形の YAML に書き出す。決裁事項(何を頼むか)と制約(上限額・時期・対象の範囲)は、本文の文のまま独立した欄に写す。あとの工程(組み直す・端的・丁寧)が「保つもの」としてこの2欄を読む。論点は本文の節(見出し)ごとに1つにし、節の中の段落や文を別の論点に分けない(分けると、段落ごとの小さな主張を直接支える根拠がそれぞれ「決裁に要る」に上がり、端的にしたときに本編が膨らむ。見出しのない文書では、話題のまとまりごと)。論点には `種類` を付ける。論証 = 主張を根拠で支える節、記述 = 事実や段取りを並べる節(費用、体制、日程、運用ルール)。`論拠` は論証にだけ書く(記述の節に論拠はないのがふつうで、書くと本当に論拠のない論点が埋もれる)。記述の節でも、並べている項目は1つずつ根拠に書き(表は行ごと)、重みを付ける(あとの工程が、何を本編に残し何を付録に回すかを重みで決めるため。付け方は下の `重み` の説明)。文書のすべての単位を、どこかの主張・根拠・前提・条件に対応づける。どれにも当てはまらない単位は、削らずに `対応なし` に行番号つきで列挙し、`理由` に「意図の分かるもの」か「分からないもの」かを書く
4. 書き手が明示していないが論が成り立つのに必要な前提は、YAML に `書き手の明示: なし` を付けて書いてよい。これは隠れた前提の検査そのもので、補った前提は報告で「本文にない言葉」と断る
5. YAML を批判的に見直し、指摘を下の5種類に分けて書き出す。文書を直さず、YAML も直さない。見直して気づいたことは、指摘の側に書く
6. YAML を、対象ファイルと同じディレクトリに `<ファイル名>.logic.yaml` として保存する。ファイルに書けない環境では、返答の中に YAML を載せる
7. 保存した YAML を `uv run <このスキルのディレクトリ>/scripts/coverage.py <文書>` にかけ、どの `行` にも現れていない非空行を見つける(表の罫線の行は数えない)。見つかった行は `対応なし` に足し、OK になるまで繰り返す。uv が使えない環境では、非空行の番号を順に YAML と突き合わせて同じことをし、そのことを報告に書く

長い文書は、節ごとにサブエージェントで分担して YAML を書き、主結論の `依存` はまとめる側が決める。指摘の重みづけは、文書全体を見て自分で決める。

Web ページを保存した文書では、ナビゲーション・パンくず・検索欄・フッターは本文ではない。`対応なし` に「サイトの部品」としてまとめて数え、指摘には使わない。

所要時間の目安は、1,000字程度で2〜4分、1万字級で10分以上。報告の冒頭に文字数と所要の目安を1行添える。

## YAML の形

```yaml
# <ファイル名> の論理構造
# 種別: 事実 = 出典やデータで確かめられること、または書き手が見聞きしたこと
#       推論 = 事実から書き手が導いたこと
#       意見 = 書き手の評価や考え
#       前提 = 確かめられていないが、論が成り立つのに必要な条件
#       見積 = 事実に係数を掛けた概算(数値があるときだけ)

文書の性格: <決めてもらう文書 / 報告する文書 / 経緯を語る文書。何を決めるか、誰が読むか>

主結論:
  主張: <文書全体で言いたいこと。本文の言葉で書く>
  行: [<対応する行番号>]
  決裁事項:
    - 内容: <読み手に決めてもらうこと。本文の文のまま。決めてもらう文書でなければ空>
      行: [<行番号>]
  制約:
    - 内容: <書き手が自分で置いている上限額・時期・対象の範囲。本文の文のまま>
      行: [<行番号>]
  比べた案:
    - 内容: <本文に書かれた、選んだ案以外の案(何もしない、既存のツール、無料版のまま、など)。本文の言葉で。なければ「なし」の1件だけ>
      行: [<行番号>]
  前提:
    - 種別: 前提
      内容: <本文の言葉>
      行: [<行番号>]
      書き手の明示: <あり / なし。なしなら本文にない言葉で補ったもの>
  依存: [<論点の名前>, ...]

論点:
  - 名前: <短い名前。本文の見出しがあればそれ>
    種類: <論証 / 記述>
    主張: <本文の言葉。記述なら、その節が何を並べているかを1行で>
    行: [<行番号>]
    論拠: <論証だけ。なぜこの根拠からこの主張が言えるのか。1行。本文に書いてあればその言葉、なければ「本文にない」と書く。記述ではこの欄を省く>
    根拠:
      - 種別: 事実
        内容: <本文の言葉>
        行: [<行番号>]
        重み: <決裁に要る / 裏づけ / 補足>
      - 種別: 推論
        内容: <本文の言葉>
        行: [<行番号>]
        重み: <決裁に要る / 裏づけ / 補足>
    並列:
      切り口: <項目を何で分けているか。1行で(例: 期間で分けている)。並列がなければこの欄ごと省く>
      項目:
        - 内容: <本文の言葉>
          行: [<行番号>]
    限界や条件:
      - 内容: <本文に書かれている限界・条件。書かれていなければこの欄は空>
        行: [<行番号>]

対応なし:
  - 行: <行番号>
    内容: <本文の言葉>
    理由: <意図の分かるもの(タイトル・挨拶・問いかけ・表の区切り・サイトの部品) / 分からないもの>
```

`比べた案` は、決裁者が最初に聞く「ほかになかったのか」に答える欄で、本文に書かれた案を名前と行番号で写すだけ(重みや採点は書かない)。somosomo の「他の選択肢」の問いと、端的にするときに残す根拠が、この欄を見る。`種類` は、論点が主張を根拠で支えている(論証)か、事実や段取りを並べている(記述)か。稟議書なら、背景・期待効果・費用対効果は論証、費用の表・体制・日程・運用ルールは記述になることが多い。`論拠` は、根拠と主張のあいだの橋で、Toulmin の論証モデルでいう warrant にあたる。本文に書かれていないことが多く、そのときは「本文にない」と書く。これは隠れた前提の検査であり、「もっと端的に」で残す根拠を選ぶ基準にもなる。`重み` は、決める人がその根拠を読まないと決められないか(決裁に要る)、決めたあとに裏づけとして見たいか(裏づけ)、なくても判断が変わらないか(補足)の3つ。「もっと端的に」が本編に残すか付録に回すかをこの欄で決めるので、読んだ印象ではなく次の当てはめで付ける。

- 論証の論点では、主張がそこから直接出る根拠だけを「決裁に要る」にする。主張の数値がその根拠の計算から出る、主張がその観測から導かれる、というもの。同じ主張を別の角度から支える根拠(他社の例、試用の評判)は「裏づけ」、場面の説明(いまの作業の手順)は「補足」。根拠が鎖になっているときは、主張の直前の一歩だけが「決裁に要る」で、その前の歩は「裏づけ」。ただし、前提の数値から結果の値までひと続きの計算(「1件30分 × 月20件 × 12か月 = 120時間、× 4,000円 = 480,000円」)は、途中の値を別の根拠に割らず、前提と結果を含む1つの根拠にまとめて書く(端的にしたとき、前提の数値が結果と一緒に本編に残る)。文を分けて書いてある根拠まで1つにまとめることはしない例: 「月に20件の問い合わせがある(裏づけ)→ 回答の下書きに時間がかかっている(裏づけ)→ この作業が窓口担当の残業の主な原因になっている(決裁に要る)→ 主張: 外注の目的は窓口担当の残業を減らすこと」。根拠が1つしかない論点でも、この当てはめで決める(1つだからという理由で「決裁に要る」にすると、端的にしたときに本編が縮まない)
- 記述の論点では、`決裁事項` か `制約` の値そのもの、その値を作る項目(上限額の内訳の各行、合否を分ける判定基準の閾値)、`決裁事項` が承認を求めている対象そのもの(「総務に点検を担わせる」が決裁事項なら、その点検のルール)を「決裁に要る」にする。数値のないリスクの一覧、段取り、体制、報告の方法は「裏づけ」
- 決裁事項をそのまま並べた節(「承認依頼事項」「お願いしたいこと」)は論点にしない。その行番号は主結論の `決裁事項` に入れる(論点にすると、端的にしたときに決裁事項が二度書かれる)

`内容` には本文の言葉をそのまま、または最小限の言い換えで書く。文と文の関係(「〜だから」「〜にもかかわらず」)も、本文にあるものだけを書く。要約で足した関係は、書き手の論ではなく読み手の論になる。種別は上の5つだけを使う。

## 指摘の5種類

1. 矛盾:主張どうし、主張と根拠、数値どうし、冒頭と結びが食い違う(「対象を『50代前半』と書いているが、根拠の1社は55歳以上」「冒頭は意識の変化が重要と言い、まとめの3項目は制度とツールだけ」)。確信の度合いが段落によって違うものもここに入る。日付・時刻・件数・割合は、文書の別の場所(報告日や作成日、表の数字、本文の計算)と突き合わせる。報告日より後の日付が「実施済み」になっている、表の時刻の差と本文の所要時間が合わない、件数から出る割合と本文の割合が合わない、といった食い違いは、文の中だけを読んでいると見落とす
2. 根拠のない主張:主張に対応する根拠が YAML 上にない、または根拠の種別が意見・前提だけで事実がない。本文の支えがない見出しもここに入る。問いを書くときは、飛躍の原因がどれかを見分けて聞く
   - 前提条件のちがい:書き手には当たり前でも、読み手が共有していない前提がある(「月2時間の削減は、何の測定から来た数字か」)
   - 異質なものの同質化:別のものを一括りにしている(「最高益なのは1社で、もう1社は黒字。2社とも最高益の年として扱っていないか」)
   - 偶然の必然化:少数の事例や不確かな段階の連なりを、必然のように言い切っている(「2社の事例から『時代は終わった』と言える根拠が文書の中にあるか」)
3. 事実と推論の混在:推論や意見が、事実と同じ言い方で書かれていて、読み手が区別できない(「会社の動機は推論だが『〜する』と事実の形で書かれている」)。種別を分けるときに迷った箇所がここに入る
4. 横の論理(並列の漏れ・ダブり・ねじれ):並べられた項目の切り口が途中で変わる、同じものが2つの切り口で2回出る、レベルの違うものが同列に並ぶ(「行45では短期と中長期の2区分、行132では即効・中期・投資判断の3区分。どちらの切り分けか」)。漏れは、全体が何かを文書が言っているときだけ指摘できる(「3つの課題と言っているが、本文には2つしかない」)
5. どこにも対応しない文:`対応なし` のうち「分からないもの」。意図の分かるもの(タイトル、挨拶、問いかけ、表の区切り、サイトの部品)は件数だけ報告する

どの指摘も、行番号と、書き手への問いの形で書く。直し方(「弱めるべき」「条件を足すべき」)を決めるのは書き手。

## 出力の形式

SKILL.md の共通形に従う。指摘の見出しは上の5種類。`対応なし` は「意図の分かるもの n 件(内訳)」「分からないもの n 件」と分けて数える。補った前提があれば、その旨を主結論の直後に1行で断る。

指摘は YAML の転記ではなく、文書の文脈に即して書く。
