# somosomo:文書の外から、そもそも前提が合っているかを問う

logic が文書の中で筋が通っているかを見るのに対し、somosomo は文書の外に立って問う。「そもそもこの前提は合っているか」「そもそもこれは解くべき問いか」「他の道はないか」「何が起きたら倒れるか」。決裁者やレビュアーが会議室で投げる問いを、提出前に書き手に返すモード。

このモードは文書にない観点を持ち込む。だからこそ、持ち込んでよいものの線をはっきりさせる。

- 持ち込んでよい:問い、その前提が崩れたとき文書のどこが倒れるか、問いを閉じるのに要る材料の種類
- 持ち込まない:代替案の中身、文書にない事実や数値、結論、直し方。「競合の X を検討すべき」とは書かず、「他の選択肢を検討したか。検討したなら、比較の記録はあるか」と書く。「〜を入れて出し直してほしい」「〜を書き足すとよい」のような直し方は、指摘にも反論にも結びにも書かない。何を足すかは書き手が決める

## 手順

1. 対象ファイルの隣に `<ファイル名>.logic.yaml` があれば読む。なければ、先に logic.md の手順で YAML を作る。somosomo の問いは、主結論と論点と前提を足場にする。足場がないと「本当にそうですか」が並ぶだけになる
2. YAML の前提(`書き手の明示: なし` のものを含む)、主結論、各論点の主張を1つずつ取り、下の5つの問いを当てる。当てはまらない問いは飛ばす
3. 指摘は「問い・倒れる場所・要る材料」の3点で書く
   - 問い:書き手への問い。本文の言葉を使う
   - 倒れる場所:その前提が崩れたとき、文書のどの行の主張が立たなくなるか。行番号で
   - 要る材料:問いを閉じるのに足りる材料の種類(「対象20名の直近1か月の作業記録」「同種ツールの他社の継続率」)。材料の中身は書かない
4. 文書全体で効くものから順に並べる。目安は5〜8件。細かいものは数えるだけにする
5. 任意で、反対の立場からの読みを1〜2本書く。「反論」と明示し、文書の主張を否定する立場の人がどの行をどう読むかを書く。反論にも指摘と同じく行番号を付け、行番号で指せない反論は書かない。これは書き手の主張ではなく検査のための仮の立場で、採用するかは書き手が決める。仮の立場の中でも「〜すべき」「〜した方がよい」の形は使わず、「〜という読みが成り立つ」「〜と読める」の形で書く。邪魔なら書かない
6. YAML を直さない。somosomo の指摘は返答にだけ書く

## 5つの問い

1. 前提:その前提は合っているか。書き手が当たり前と思っているが、読み手が共有していない前提はどれか。`書き手の明示: なし` の前提はまずここで問う(「2社の事例が会社一般に当てはまる、という前提で書かれている。そう言える材料はあるか」)
2. 問いそのもの:そもそもこれは解くべき問いか。表面の現象を課題と取り違えていないか。文書が答えている問いと、読み手(決裁者)が決めたいことが同じか。文書は読み手に何を求めているか(共有だけか、判断か)、求めているなら何を決めてほしいのかが書かれているか(「この稟議は『ツールを入れるか』に答えているが、決裁者が知りたいのは『残業を減らせるか』ではないか」)
3. 他の選択肢:他の道を検討したか。何もしない案と比べたか。比べたなら、その記録は文書に出せるか。比べる相手として名指ししてよいのは「何もしない」「元に戻す・やめる」「自前でやる」「範囲を変える」のような型だけで、その領域の専門知識から具体的な代替案(別の技術、別の製品、別の手順)を挙げない。それは代替案の中身を持ち込むことになる。ただし、文書自身が書いている案(試した無料版、比較した既存ツールなど)を名指しして「その案のまま続ける道は比べたか」と問うのは持ち込みではない
4. 覆る条件:何が起きたら、この結論は倒れるか。文書は、その条件を自分で書いているか。書いていないなら、書き手はそれを知っているか(「月2時間の削減が月1時間なら、行72の損益分岐を越えない。この数字はどのくらい確かか」)
5. 利害と実行:誰にとっての利益か。不利益を受けるのは誰か。誰がやる想定か。やる人は文書を読んで、自分がやると分かるか

## 出力の形式

SKILL.md の共通形に従う。指摘の見出しは上の5つの問い。各指摘は、問い・倒れる場所(行番号)・要る材料の3点。反論を書いた場合は、指摘のあとに「反論(仮の立場)」の見出しで分けて置く。

結びには、logic との違いを1行添える。「ここで挙げたのは文書の外からの問いで、文書の中の矛盾は `/critical-thinking logic` で見る」
