# somosomo:文書の外から、そもそも前提が合っているかを問う

logic が文書の中で筋が通っているかを見るのに対し、somosomo は文書の外に立って問う。「そもそもこの前提は合っているか」「そもそもこれは解くべき問いか」「他の道はないか」「何が起きたら倒れるか」。決裁者やレビュアーが会議室で投げる問いを、提出前に書き手に返すモード。

このモードは文書にない観点を持ち込む。だからこそ、持ち込むものの線をはっきりさせる。

- 持ち込むのは3つ:問い、その前提が崩れたとき文書のどこが倒れるか、問いを閉じるのに要る材料の種類
- 書き手に残すもの:代替案の中身、文書にない事実や数値、結論、直し方。「競合の X を検討すべき」ではなく「他の選択肢を検討したか。検討したなら、比較の記録はあるか」と書く。「〜を入れて出し直してほしい」「〜を書き足すとよい」のような直し方は、指摘にも反論にも結びにも入れない。何を足すかを決めるのは書き手で、こちらが決めると書き手の文書でなくなる

## 手順

1. 対象ファイルの隣に `<ファイル名>.logic.yaml` があれば読む。なければ、先に logic.md の手順で YAML を作る。somosomo の問いは、主結論と論点と前提を足場にする。足場がないと「本当にそうですか」が並ぶだけになる
2. YAML の前提(`書き手の明示: なし` のものを含む)、主結論、各論点の主張を1つずつ取り、下の5つの問いを当てる。当てはまらない問いは飛ばす
3. 指摘は「問い・倒れる場所・要る材料」の3点で書く
   - 問い:書き手への問い。本文の言葉を使う
   - 倒れる場所:その前提が崩れたとき、文書のどの行の主張が立たなくなるか。行番号で
   - 要る材料:問いを閉じるのに足りる材料の種類(「対象20名の直近1か月の作業記録」「同種ツールの他社の継続率」)。材料の中身は書かない
4. 指摘を並べる前に、「決裁者の論点」を1行で書く。この文書で決裁者が決めること(答えが「いいえ」なら決裁事項が成り立たなくなる問い)を一文で。YAML の `決裁事項` の欄(何を頼むか)から立てる。「主結論」は文書が頼んでいることで、「決裁者の論点」は読み手がそれを決めるために答えを要することなので、別物として書く。報告や経緯の文書では、読み手がこの文書を読んで判断すること(共有だけか、何かを変えるか)を書く
5. 5つの問いで見つけた指摘のうち、決裁者の論点を倒しうるもの(答えしだいで決裁事項が成り立たなくなるもの)を最大3件選び、「決裁事項を倒しうる問い」の見出しで先頭に移す。各指摘に、どう倒れるかを1行添える。残りの指摘は、下の5つの問いの順で続ける(先頭に移した問いは、そこから外す)。先頭の3件は見つけた指摘から選び、3件に満たなければそのままでよい。全体は5〜8件を目安に、細かいものは件数で示す。読む人が答える問いの数に限りがあるためで、見つけた指摘はすべて挙げたうえで、効くものから順に並べる
6. 任意で、反対の立場からの読みを1〜2本書く。「反論」と明示し、文書の主張を否定する立場の人がどの行をどう読むかを書く。反論にも指摘と同じく行番号を付ける(行番号で指せない反論は、書き手が確かめられない)。これは書き手の主張ではなく検査のための仮の立場で、採用するかは書き手が決める。仮の立場の中でも、「〜という読みが成り立つ」「〜と読める」の形で書く(「〜すべき」「〜した方がよい」は直し方になる)。反論でも、手段や施策は型までにとどめる。「問題は道具ではなく引き継ぎのやり方にある、という読みが成り立つ」までで、そのやり方の中身(期間、同行、様式など)は書き手に残す。邪魔なら書かない
7. YAML はそのまま残し、somosomo の指摘は返答にだけ書く(足場を書き換えると、logic の検査と食い違う)

## 5つの問い

1. 前提:その前提は合っているか。書き手が当たり前と思っているが、読み手が共有していない前提はどれか。`書き手の明示: なし` の前提はまずここで問う(「2社の事例が会社一般に当てはまる、という前提で書かれている。そう言える材料はあるか」)
2. 問いそのもの:そもそもこれは解くべき問いか。表面の現象を課題と取り違えていないか。文書が答えている問いと、読み手(決裁者)が決めたいことが同じか(YAML の `決裁事項` と、論証の論点が答えていることを突き合わせる)。文書は読み手に何を求めているか(共有だけか、判断か)、求めているなら何を決めてほしいのかが書かれているか(「この稟議は『ツールを入れるか』に答えているが、決裁者が知りたいのは『残業を減らせるか』ではないか」)。読み手や書き手の手元にある材料で確かめられることを、外注・投資・承認の前提にしていないか。確かめてから頼めることを、頼んでから確かめる形になっていないか(「失注の件数と金額は御社の台帳から出せるのに、それを出す作業を900万円の診断に含めている」)
3. 他の選択肢:他の道を検討したか。YAML の `比べた案` が「なし」なら、何もしない案・小さく始める案・別の手段と比べたか、比べたなら記録は文書に出せるかを問う。案があれば、その案を名指しして、何を軸に比べ、選んだ理由が本文のどこにあるかを問う。比べる相手として名指しするのは「何もしない」「元に戻す・やめる」「自前でやる」「範囲を変える」のような型と、文書自身が書いている案(試した無料版、比較した既存ツールなど)。その領域の専門知識から出る具体的な代替案(別の技術、別の製品、別の手順)は、代替案の中身を持ち込むことになるので、型にとどめる
4. 覆る条件:何が起きたら、この結論は倒れるか。文書は、その条件を自分で書いているか。YAML の `制約`(上限額・時期・対象)は書き手が自分で置いた線で、その線を越える条件を文書が想定しているかも問う。書いていないなら、書き手はそれを知っているか(「月2時間の削減が月1時間なら、行72の損益分岐を越えない。この数字はどのくらい確かか」)
5. 利害と実行:誰にとっての利益か。不利益を受けるのは誰か。誰がやる想定か。やる人は文書を読んで、自分がやると分かるか。効果を測る数字を、利益を受ける側の自己申告に頼っていないか。判断を下す人と、その判断で利益を得る人が同じになっていないか(診断する側が導入も受注する、評価する人が起案者でもある)

## 出力の形式

SKILL.md の共通形に従う。「文書の性格」「主結論」の次に「決裁者の論点」を1行置く。指摘は「決裁事項を倒しうる問い」(最大3件)を先頭に、続けて上の5つの問いの見出しで並べる。各指摘は、問い・倒れる場所(行番号)・要る材料の3点。反論を書いた場合は、指摘のあとに「反論(仮の立場)」の見出しで分けて置く。

結びには、logic との違いを1行添える。「ここで挙げたのは文書の外からの問いで、文書の中の矛盾は `/critical-thinking logic` で見る」
