# critical-thinking

仕事の文書の「考え」を検査するスキル。文書の中で筋が通っているか(logic)と、文書の外から見て前提が合っているか(somosomo)の2つを分けて見る。natural-japanese が日本語を直すのに対し、このスキルは中身を見る。

## 約束

- 文書を書き換えない。YAML と指摘を返すだけで、直すかどうかは書き手が決める
- 文書にない事実・数値・代替案の中身を足さない。somosomo では「どんな材料があれば問いが閉じるか」の種類までは書くが、材料そのものと結論は書かない
- 指摘は書き手への問いの形で書く。「弱めるべき」「条件を足すべき」とは書かない
- 指摘はすべて行番号で文書に紐づける。行番号で指せない指摘は書かない

## 呼び出し方

- `/critical-thinking logic <ファイル>`:文書の中で筋が通っているかを検査する。論理構造を YAML に書き出し、主張と根拠の対応、矛盾、事実と推論の混在、並列の漏れやねじれ、どこにも対応しない文を指摘する。最初に `references/logic.md` を読む。YAML の漏れは `scripts/coverage.py` で確かめる
- `/critical-thinking somosomo <ファイル>`:文書の外から前提を疑う。主結論と論点を足場に、前提・問いそのもの・他の選択肢・覆る条件・利害と実行を問う。`<ファイル>.logic.yaml` が隣にあればそれを使い、なければ先に logic の YAML を作る。最初に `references/somosomo.md` を読む

モードの指定がなければ、依頼の言葉で選ぶ。「矛盾がないか」「論理が通っているか」「根拠を確かめて」「ロジックが弱い」は logic。「そもそも」「前提を疑って」「本当にそうか」「他の選択肢は」「決裁者目線で」「穴を探して」は somosomo。どちらとも取れなければ logic を先にやり、somosomo を続けるか聞く。

## 出力の共通形

1. 文書の性格を1行(何を決める文書か、誰が読むか。振り返りや経緯の記述なら、そう書く)
2. 主結論を1〜2文で。書き手の意図とずれていそうなら添える
3. 指摘を種類ごとに。各指摘は、行番号・本文の言葉・書き手への問い。文書全体で効くものから順に並べ、些末なものは数えるだけにする
4. YAML の保存先
5. 結び:「直すかどうかは書き手が決める。直すなら `/natural-japanese <ファイル>` で推敲できる」

同じ文書を2回検査すると、指摘の数や言い方は揺れる。LLM の読みに頼る検査の限界で、lint のような再現性はない。結果に一言添える。

## 指摘を反映して直すよう頼まれたとき

検査のあとに「指摘を反映して直して」と頼まれることがある。これは検査とは別の工程で、約束の「書き換えない」は検査の側の話。直すときは、問いに全部答えて本文に書き足すと、文書は長くなり、決める人が読む分量が増える。次の順で直す。

1. 決める人の論点を1つに決める。この文書を読んで何を決めるか(「PoC の予算を出すか」)。本編は、その判断に要る節だけで組む。見出しは元の文書と同じ短い名詞句のままにし(「費用対効果」)、文や数字や【要確認】を見出しに入れない。結論は各節の最初の一文に書き、見出しと最初の一文だけ読んで筋が通るようにする
2. 答えられる問いは、本文の該当箇所を直して答える。矛盾はどちらかに揃え、計算は直す。文書にない事実は作らない
3. 答えられない問い(出典、実データ、まだ決まっていないこと)は、本文に書き足さず、末尾の「確認事項」に1行ずつ並べる。本文では言い切りを仮定の形(「仮に月3時間とすると」)に変えるだけにする
4. 計算の前提、方式の比較表、機能要件、試算の感度表のような、判断の裏づけだが読まなくても決められるものは、付録に回す
5. 改訂の経緯(「第1版では〜としていた」)は書かない。読む人は改訂の前を知らない

直したあとに、元の文書より長くなっていたら、1 に戻って本編から外せる節を探す。

## 参考にした枠組み

縦の論理(本当にそうか)と横の論理(それだけか)、飛躍の3つの原因は高田貴久『ロジカル・プレゼンテーション』、問いそのものを疑う見方は内田和成『論点思考』から借りている。言い回しは借りず、問いの型だけを使う。
