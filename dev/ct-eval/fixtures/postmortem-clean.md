# 受注管理システム 応答停止の障害報告

報告日:2026年10月23日
報告者:情報システム部 運用チーム(担当:運用リーダー)

## 1. 概要

10月21日(水)10:12 から 11:48 まで、受注管理システムの Web 画面が応答しなかった(影響時間1時間36分)。この間に入力が試みられた注文は312件で、うち41件(13%)が入力に失敗した。失敗した41件は営業担当が顧客に連絡して再入力を依頼し、当日中に入力を終えた。顧客には連絡と再入力の手間が生じている。

## 2. 経緯

| 時刻 | 事象 |
|---|---|
| 10:12 | 監視アラート(応答時間5秒超)が発報 |
| 10:20 | 運用担当が調査を開始 |
| 10:35 | アプリサーバー2台のメモリ使用率が95%を超えていることを確認 |
| 11:05 | アプリサーバーを1台ずつ再起動 |
| 11:48 | 全画面の応答を確認し、復旧とした |

再起動後に応答時間が通常に戻ったことから、メモリ不足が直接の原因だと見込み、10月22日に検証環境で確かめた(3節)。

## 3. 原因

### 発生の原因

10月20日に本番へ反映した注文検索の改修で、検索結果をキャッシュする処理に件数の上限がなかった。10月22日に検証環境で同じ改修を入れて検索を繰り返したところ、メモリ使用率が1時間で40%から93%まで上がり、本番と同じ応答停止が再現した(検証記録、開発チーム)。上限を1,000件にすると、同じ操作で使用率は55%で頭打ちになった。

この改修は担当者1名が実装し、レビューなしで本番に反映していた。開発チームの手順では本番反映前のレビューを求めているが、急ぎの改修は担当者の判断で省略できる運用になっていた。

### 検知と復旧が遅れた原因

監視アラートの通知先が運用担当1名の個人宛メールだけで、担当者が会議中だったため、調査の開始がアラートから8分遅れた。

## 4. 再発防止策

| 対策 | 対応する原因 | 担当 | 期限 |
|---|---|---|---|
| 検索結果のキャッシュに1,000件の上限を設ける | 発生(キャッシュ) | 開発チーム(担当:検索機能の担当者) | 10月22日に実施済み |
| 急ぎの改修でもレビューを省略できないよう手順を改める | 発生(レビュー省略) | 開発チームリーダー | 10月31日 |
| アラートの通知先を運用チームの共有チャンネルにする | 検知の遅れ | 運用リーダー | 10月24日に実施済み |
| メモリ使用率が80%を超えたらアラートを出す | 検知の遅れ | 運用リーダー | 10月31日 |

キャッシュの上限で、同じ経路の再発は検証環境で起きないことを確かめた。別の経路でメモリが増える場合は、80%のアラートで応答停止の前に検知することを狙う。

## 5. 判断を求める事項

1. 再発防止策の2(レビュー省略の禁止)を、開発チームの標準手順として承認すること
2. 失敗した41件の注文について、顧客への説明を営業部から行うかどうかを、営業部長が10月28日の部内会議で決めること

## 6. 今後の予定

10月28日の部内会議で、本報告の内容を共有し、上の2点の判断を仰ぐ。
