# 受注管理システム 応答停止の障害報告

報告日:2026年10月23日
報告者:情報システム部 運用チーム

## 1. 概要

10月21日(水)10:12 から 11:48 まで、受注管理システムの Web 画面が応答しなくなった。影響時間は1時間20分で、この間に入力された注文は312件、うち入力に失敗した注文は41件だった。顧客からの問い合わせはなかったため、顧客への影響はなかった。

## 2. 経緯

| 時刻 | 事象 |
|---|---|
| 10:12 | 監視アラート(応答時間5秒超)が発報 |
| 10:20 | 運用担当が調査を開始 |
| 10:35 | アプリサーバー2台のメモリ使用率が95%を超えていることを確認 |
| 11:05 | アプリサーバーを1台ずつ再起動 |
| 11:48 | 全画面の応答を確認し、復旧とした |

再起動後に応答時間が通常に戻ったため、原因はメモリ不足と判断した。

## 3. 原因

障害の原因は次の3つである。

- 10月20日に本番へ反映した注文検索の改修で、検索結果をキャッシュする処理に上限がなく、検索のたびにメモリが増え続けたこと
- この改修を担当者1名が実装し、レビューなしで本番に反映したこと
- 監視アラートの通知先が運用担当1名の個人宛メールだけだったこと

キャッシュに上限がなかったことがメモリを増やし続け、2台のサーバーを同時に応答不能にした。

## 4. 影響

注文312件のうち、入力に失敗した注文は41件で、全体の1割未満にとどまった。失敗した注文は、営業担当が顧客に連絡して再入力を依頼し、当日中にすべて入力を終えた。

## 5. 再発防止策

| 対策 | 担当 | 期限 |
|---|---|---|
| 検索結果のキャッシュに件数の上限を設ける | 開発チーム | 10月24日(実施済み) |
| メモリ使用率が80%を超えたらアラートを出す | 運用チーム | 10月31日 |
| アラートの通知先を運用チームの共有チャンネルにする | 運用チーム | 10月31日 |
| アプリサーバーの再起動手順を整備する | 運用チーム | 11月中 |
| 本番反映前のレビューを必須にする | 検討中 | 未定 |

上の対策により、同種の障害は再発しない。

## 6. 今後の予定

10月28日の部内会議で、本報告の内容を共有する。
