決裁者に出す文書を、出す前に決裁者の目で読み直すスキル critical-thinking を追加しました

AI に稟議書や提案書を書かせると、前提を疑わないまま結論まで走った文書ができます。上司や経営会議に「そもそも原因はそれなのか」「この数字はどこから」と差し戻される。考えの穴なので、日本語を直しても埋まりません。

critical-thinking に「決裁者の目で見て直して」と頼むと、文書を決裁者の立場で読み、文書の中で答えが出ることは黙って直し、起案者にしか答えられないことだけを3つ聞いて、答えを本文に入れた文書を返します。事実は足さず、起案者の代わりに決めません。

例: コンサル会社が食品卸に出す架空の提案資料(営業のデジタル化支援、9か月・2,700万円)。スキルなしの Claude Code に書かせたもの。

元の文

御社ではこの引き継ぎの場面で実際に失注が起きています。

だから SFA(営業支援システム)を入れる、という提案の前提。

スキルの問い 起案者にしか答えられない

「引き継ぎの場面で実際に失注が起きている」は、何をもとに書きましたか。件数や金額で、いま分かっていることはありますか。

起案者の答え

営業本部長が「引き継ぎで2社失った」と話したのを聞いたことがもとです。失注の理由を確かめた記録はなく、件数と金額は分かりません。

直した文

営業本部長からは、この引き継ぎで2社を失ったとうかがっています。ただ、その理由はまだ確かめていません。

答えを強めず弱めず、出どころを添えて本文に入れた。聞いた話を前提にした提案だと、読む人に分かる。

何をするか

対象は、稟議書、企画書、提案資料、障害報告書のような、読んだ人に判断を求める文書です。natural-japanese が言い回しを直すのに対し、critical-thinking は論の筋を見ます。各項目を押すと説明が出ます。

文書

このページの例は、スキルなしの Claude Code(Opus 5.5)に短い依頼文から書かせた架空の稟議書・制度企画・提案資料です。わざと穴を作らせたのではなく、書かせたままの文書です。どれも丁寧に書かれていて、稟議書は1名1件の試行を「参考値」と断り、開始前に基準を測る設計まで入っています。

筋を見る

文書の中だけで読み、矛盾、根拠のない主張、事実と推論の混在、挙げた項目の抜けや食い違いを、行番号つきの問いにします。稟議書の例では18件でした。

前提を疑う

決裁者の立場で読み、決裁者が何を決める文書かを1行で押さえたうえで、前提は妥当か、解こうとしている課題の立て方は合っているか、他の選択肢と比べたか、何が起きたら結論が覆るか、誰が実行するかを問います。決裁事項を覆しうる問いを3つまで先頭に置きます。稟議書の例では14件でした。

起案者に3つだけ聞く

2つの検査の問いのうち、文書の中で答えが出るもの(矛盾、計算、言い切りの強さ、並べて挙げた項目どうしの食い違い)は聞かずに直します。起案者に聞くのは、文書にない事実、決裁者に何を決めてもらうつもりか、どこまで頼むか、のように起案者にしか答えられないことだけで、3つまでです。「分からない」という答えも答えです。

直した文書

起案者の答えを、強めず弱めず、出どころを添えて本文に入れます。「分からない」だった箇所は仮定の形にします。文書の中で直せる指摘はすべて直し、裏づけの試算や体制は付録に移します。残りの問いは文書の中には書かず、別のファイル(稟議書.確認事項.md)に「先に答える問い」3件までと「そのほか」に分けて出します。直した文書には、直した箇所の印も確認事項の節も入らないので、そのまま出せます。事実は足さず、起案者の代わりに決めず、本編を元より長くしません。頼み方:「稟議書.md を決裁者の目で見て直して」

検査のあとに別に頼みます。事実・数値・主結論・決裁を求める事項は保ったまま、論の組み立てだけを替えます。構成案を2〜3つ出し、そのうち1つは必ず決裁の範囲を絞る案で、起案者が選んだ案で書きます。頼み方:「構成から組み直して」

検査は8本すべてに、直す・組み直すは欠陥ありの4本に、決裁者の目で見て直すは稟議書と提案資料の2本に、3回ずつかけました。決裁者の目で見て直すでは、起案者だけが知っている事実の一覧を作者が先に書き、別のセッションの Claude がその一覧だけを見て起案者の役で答えました。一覧にないことは「分からない」と答えます。合否は「欠陥ごとに3回中2回以上、問いが欠陥を捉えた」で見ていて、対象の56か所はすべて合格でした。59か所のうち3か所(稟議書・障害報告書・提案資料に1か所ずつ)は、仕込んだときに「細かすぎて見つからなくても不合格にしない」と決めた欠陥で、合否の計算からは外していますが、上の延べ回数には含めています。

表の「直す」は、起案者に聞かずに検査の指摘だけで直す工程で、「決裁者の目で見て直す」の中でも使われます。「組み直す」は、直すの決まりに加えて論の組み立てを替える工程なので、仕込んだ欠陥の扱いは直すと同じ数え方で見ています。

検査の2工程(筋を見る・前提を疑う)は、確認事項を別ファイルに出す前の版で測り、最終版では測り直していません。最終版で変えたのは直す側の規則だけで、検査の規則は変えていないためです。「決裁者の目で見て直す」「直す」「組み直す」は最終版で測りました。

測りながら規則を4つ直しました。「前提を疑う」が提案資料に対して1度、「引き継ぎ期間や同行訪問で解ける」のように文書にない手段を代案として挙げたので、代案でも手段の名前は出さないようにしました。「直す」が障害報告書で1度、文書の別の箇所にある事実を結論の新しい根拠としてつないだので、根拠として挙げてよいのは文書がそう書いているものだけにしました。「組み直す」は、3本とも段取りを替えるだけの案に収束したので、決裁の範囲を絞る案を必ず出すようにしました。「決裁者の目で見て直す」は、提案資料で起案者の答えを入れた分だけ本編が1〜4%長くなる回が続いたので、答えを入れた字数と同じだけ、要らなくなった断り書きを削るようにしました。それでも提案資料では、答えが「分からない」のときに「台帳から確かめる」のような新しい段取りを書き足す回が続いたので、元の文書にある確かめ方の文をそのまま使う規則を足しました。あわせて、答えを入れる工程なので本編の上限を「元の本編+答えの字数」に改めました。提案資料はこれらを直しながら5回(各3本)測り、表には最後の回を載せています。稟議書も最後の規則で測り直しました。測り方と回ごとの結果は dev/ct-eval/RESULTS.md にあります。

苦手なこと

  • 文書の外の事実は調べに行きません。稟議書が挙げる他社の事例が本当かは、問いにして返すだけです。
  • 起案者に聞くのは3つまでなので、聞かなかった問いは別ファイルの確認事項に残ります。稟議書の例では20件でした。3つに答えただけでは、文書は決裁者に出せる形に近づきますが、確認事項が空になるわけではありません。
  • 本編が劇的に変わる場面は少なく、直しの大半は、答えを本文に入れる、言い切りを仮定の形に変える、試算を付録に移す、の3種類です。決裁事項そのものを変える案は「組み直す」で出しますが、選ぶのは起案者です。制度企画では、組み直しても節の並べ替えにとどまったと判定された回が3回のうち2回ありました。
  • 検査は LLM の読みに頼るので、同じ文書をもう一度検査すると、指摘の数や言い方は揺れます。
  • 「直す」には、根拠があるのに弱腰な言い方を言い切りに戻す決まりもありますが、AI が書いた下書きには、根拠があるのに弱く言っている箇所がほとんどなく、わざと強い言い切りで書かせた提案資料でも出番はありませんでした。弱める方向にしか働いていません。

インストールと頼み方

使う環境を選んでください。頼み方はどの環境でも同じで、文書のファイルを示して「稟議書.md を決裁者の目で見て直して」と頼みます。スキルが3つまで質問するので、答えると直した文書が返ります。工程を分けて使いたいときの頼み方は、次の3つです。

  • 検査だけ:「稟議書.md の筋が通っているか検査して」「稟議書.md を決裁者目線で、前提から疑って」
  • 検査のあとで、聞かずに直す:「指摘を反映して直して」
  • 論の組み立てから替える:「構成から組み直して」
