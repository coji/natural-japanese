# 受注管理システム障害報告書(10月21日発生分)

宛先:情報システム部長、営業本部長
作成:情報システム部 運用チーム

## 判断のお願い

10月21日の障害は復旧しましたが、メモリが上限に達した原因はまだ確定していません。決めていただきたいことは次の2つです。

1. 再発防止の3つの方向でよいか
2. 受注検索の改修が原因かどうかの調査に1週間かけてよいか

防止策の具体的な内容、担当、期限はまだ決まっておらず、調査の結果が出てから改めて出したいと考えています。

## 起きたこと

10月21日(火)の午前中、受注管理システムの Web 画面が1時間半ほど応答しなくなりました。サーバーを再起動し、11:50 ごろに復旧しました。

この時間帯に営業が入力した注文は約300件で、そのうち約40件(約13%)が入力に失敗しました。失敗した分は、営業が顧客に再入力を頼みました。注文を入力するのが営業か顧客かは確認中です。顧客からの問い合わせはありませんでしたが、約40件の分は顧客に再入力の手間をかけています。

残りの約260件は入力できています。画面が応答しなかった時間帯にも入力できた注文があることになり、止まり方が全面的だったのか断続的だったのかは確認中です。

## 現在の状態

10月28日の時点で再発はありません。再起動後はメモリ使用量を1時間ごとに見ています。受注検索の改修は切り戻しておらず、本番に残っています。

## 原因

直接の原因は、アプリケーションサーバー(受注管理システムの処理を動かすサーバー)のメモリが上限に達したことと見ていますが、上限に達した理由は確定していません。調査でこの状態を確認し、サーバーの再起動のあとに復旧しました。

疑っているのは前日の夕方に本番へ反映した受注検索の改修ですが、根拠は反映と障害の時期が近いことだけで、改修がメモリの使用量を増やしたことはまだ確かめていません。

半年前に1度、同じサーバーのメモリで通知が出たことがあります。そのときは再起動で収まり、原因は調べていません。

## 再発防止の方向

了承をお願いしたいのは次の3つの方向です。

| 再発防止の方向 | 今回の障害との関係 |
|---|---|
| 改修のメモリ使用量の確認 | 改修がメモリの使用量を増やしたことは、まだ確かめていない |
| 監視のしきい値(通知を出す基準の値)の見直し | 今回、運用チームが調べ始めたきっかけは 10:15 の通知だった |
| レビュー体制の強化 | 今回の改修のレビューは1人で行った。レビューの体制が障害につながったかどうかは、改修が原因かどうかが分かるまで判断できない |

1つ目の確認は、改修がメモリ上限到達の原因かどうかを判断する材料になります。結果によっては、ほかの2つの中身も変わることがあります。
