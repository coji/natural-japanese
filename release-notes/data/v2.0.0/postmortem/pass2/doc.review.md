# 受注管理システム障害報告書(10月21日発生分)

宛先:情報システム部長、営業本部長
作成:情報システム部 運用チーム

## 概要

情報システム部長に決めていただきたいのは、再発防止の3つの方向でよいかと、受注検索の改修が原因かどうかの調査に1週間かけてよいかの2つです。営業本部長には報告のみです。

10月21日(火)の 10:05 から、受注管理システムの Web 画面の応答が極端に遅くなりました。受注管理システムの処理を動かすアプリケーションサーバーのメモリが上限に達していて、サーバーを再起動し、11:50 ごろに復旧しました。

注文約40件が入力に失敗し、10月22日までに全件を入力し直しました。

メモリが上限に達した理由は、まだ確定していません。前日に反映した受注検索の改修を疑っています。改修は切り戻しておらず、10月28日の時点で再発はありません。

## 原因

直接の原因は、アプリケーションサーバーのメモリが上限に達したことだと見ています。調査でこの状態を確認し、サーバーの再起動のあとに復旧しました。

メモリが上限に達した理由は確定していません。疑っているのは前日の夕方に反映した受注検索の改修ですが、根拠は反映と障害の時期が近いことだけで、改修がメモリの使用量を増やしたことはまだ確かめていません。1週間の調査は、運用チームの担当者2名が検証環境で改修の前後のメモリ使用量を比べるもので、10月29日に始めて11月5日に終えます。

改修は切り戻しておらず、本番に残っています。再起動後はメモリ使用量を1時間ごとに見ていて、使用率は再起動直後が45%、その後1週間は60〜70%で推移し、増え続けてはいません。

## 影響

この時間帯に営業が入力した注文は約300件で、そのうち約13%の約40件が入力に失敗しました。失敗した分は、営業が顧客に聞き直して入力し直しました。納期の遅れが出ていないことは営業本部に確認しました。顧客からの問い合わせはありませんでしたが、約40件の分は顧客に聞き直しの手間をかけています。

残りの約260件は入力できています。アクセスログでは、応答に30秒以上かかったリクエストが全体の約8割で、全面停止ではありませんでした。

## 再発防止策

次の3つの方向を考えています。中身、担当、期限は、調査の結果が出てから改めて出したいと考えています。

| 方向 | 今回の障害との関係 |
|---|---|
| 改修のメモリ使用量の確認 | 受注検索の改修がメモリ上限到達の原因かどうかを判断する材料になる |
| 監視のしきい値の見直し | しきい値は通知を出す基準の値で、今回、運用チームが調べ始めたきっかけは 10:15 の通知だった |
| レビュー体制の強化 | 今回の改修のレビューは1人で行った。体制が障害につながったかは、改修が原因かどうかが分かるまで判断できない |

調査の結果によっては、ほかの2つの策の中身も変わることがあります。
