# 受注管理システム障害報告書(10月21日発生分)

宛先:情報システム部長、営業本部長
作成:情報システム部 運用チーム

## 概要

10月21日(火)の午前中、受注管理システムの Web 画面が1時間半ほど応答しなくなりました。アプリケーションサーバー(受注管理システムの処理を動かすサーバー)のメモリが上限に達したためで、サーバーを再起動し、11:50 ごろに復旧しました。

営業が入力した注文約300件のうち約40件が入力に失敗し、営業が顧客に再入力を頼みました。顧客からの問い合わせはありませんでした。

メモリが上限に達した原因は、まだ確定していません。前日の夕方に本番へ反映した受注検索の改修を疑っていますが、改修が原因だとは確かめられていません。再発防止策として、改修のメモリ使用量の確認、監視のしきい値の見直し、レビュー体制の強化を考えています。

## 経緯

| 日時 | 出来事 |
|---|---|
| 10月20日 夕方 | 受注検索の改修を本番に反映した。レビューは1人で行った |
| 10月21日 10:15 | 監視の通知が出て、運用チームが調べた。アプリケーションサーバーのメモリが上限に達していた |
| 10月21日 11:05 | サーバーを再起動した |
| 10月21日 11:50 ごろ | 復旧した |

通知から再起動までに50分、再起動から復旧までに約45分かかりました。

## 原因

直接の原因は、アプリケーションサーバーのメモリが上限に達したことです。調査でこの状態を確認し、サーバーの再起動のあとに復旧しました。

メモリが上限に達した理由は確定していません。疑っているのは前日の夕方に反映した受注検索の改修ですが、根拠は反映と障害の時期が近いことだけで、改修がメモリの使用量を増やしたことはまだ確かめていません。

改修のレビューは1人で行いました。レビューの体制が障害につながったかどうかは、改修が原因かどうかが分かるまで判断できません。

## 影響

この時間帯に営業が入力した注文は約300件で、そのうち約40件(約13%)が入力に失敗しました。失敗した分は、営業が顧客に再入力を頼みました。顧客からの問い合わせはありませんでしたが、約40件の分は顧客に再入力の手間をかけています。

残りの約260件は入力できています。画面が応答しなかった時間帯にも入力できた注文があることになり、止まり方が全面的だったのか断続的だったのかは確認中です。

## 再発防止策

次の3つを考えています。いずれも検討中で、具体的な内容、担当、期限はまだ決まっていません。

| 再発防止策 | 今回の障害との関係 |
|---|---|
| 改修のメモリ使用量の確認 | 受注検索の改修がメモリ上限到達の原因かどうかを判断する材料になる |
| 監視のしきい値(通知を出す基準の値)の見直し | 今回、運用チームが調べ始めたきっかけは 10:15 の通知だった |
| レビュー体制の強化 | 今回の改修のレビューは1人で行った |

改修のメモリ使用量を確認した結果によっては、ほかの2つの策の中身も変わることがあります。
