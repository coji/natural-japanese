# 受注管理システム障害報告書(10月21日発生分)

宛先:情報システム部長、営業本部長
作成:情報システム部 運用チーム

## 概要

決めていただきたいことが2つあります。再発防止の3つの方向でよいかと、受注検索の改修が障害の原因かどうかの調査に1週間かけてよいかです。

10月21日(火)の午前中、受注管理システムの Web 画面が1時間半ほど応答しなくなりました。この間に入力できた注文もあり、止まり方が全面的か断続的かは確認中です。サーバーを再起動し、11:50 ごろに復旧しました。

改修は切り戻しておらず、本番に残っています。再起動後はメモリ使用量を1時間ごとに見ていて、10月28日の時点で再発はありません。

## 原因

直接の原因は、アプリケーションサーバー(受注管理システムの処理を動かすサーバー)のメモリが上限に達したことと見ています。調査でこの状態を確認し、サーバーの再起動のあとに復旧しました。

メモリが上限に達した理由は確定しておらず、前日の夕方に本番へ反映した受注検索の改修を疑っています。根拠は反映と障害の時期が近いことだけで、改修がメモリの使用量を増やしたことはまだ確かめていません。半年前に1度、同じサーバーのメモリで通知が出たことがあります。そのときは再起動で収まり、原因は調べていません。

## 影響

入力に失敗した約40件の分は、顧客に再入力の手間をかけています。この時間帯に営業が入力した注文約300件の約13%で、営業が顧客に再入力を頼みました。入力し直すのが営業か顧客かは確認中です。

## 再発防止策

次の3つの方向でよいかの了承をお願いします。具体的な内容、担当、期限は、調査の結果が出てから改めて出します。

| 再発防止策 | 今回の障害との関係 |
|---|---|
| 改修のメモリ使用量の確認 | 改修がメモリの使用量を増やしたかは、まだ確かめていない |
| 監視のしきい値(通知を出す基準の値)の見直し | 今回、運用チームが調べ始めたきっかけは 10:15 の通知だった |
| レビュー体制の強化 | 今回の改修のレビューは1人で行った。障害との関係は、改修が原因かどうかが分かるまで判断できない |

## 付録A 経緯

| 日時 | 出来事 |
|---|---|
| 10月20日 夕方 | 受注検索の改修を本番に反映した。レビューは1人で行った |
| 10月21日 10:15 | 監視の通知が出て、運用チームが調べた。メモリが上限に達していた |
| 10月21日 11:05 | サーバーを再起動した |
| 10月21日 11:50 ごろ | 復旧した |

通知から再起動までに50分、再起動から復旧までに約45分かかりました。

## 付録B 補足

- 影響:残りの約260件は入力できています。顧客からの問い合わせはありませんでした。
- 再発防止策:改修のメモリ使用量の確認は、改修が原因かどうかを判断する材料になり、結果によっては、ほかの2つの策の中身も変わることがあります。
