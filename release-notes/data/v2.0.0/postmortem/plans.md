# 構成案(doc.md)

材料は doc.md の事実と、書き手の答え(answers.md)に限る。L と S の番号は report-logic.md と report-somosomo.md の指摘の番号で、行番号は doc.md の行。

doc.md には頼む事項がなく、YAML の `決裁事項` は空だった。書き手が answers.md で次の2つを頼みたいと答えたので、これを「頼む中身」として扱う。

- 再発防止の3つの方向でよいかの了承
- 改修が原因かどうかの調査に1週間かけてよいか

## 案1 頼む中身を小さくする案:調査の1週間だけを頼む

- **主張**:原因が確定していないので、まず改修が原因かどうかの調査に1週間かけてよいかを決めてほしい。再発防止の3つの方向は、調査の結果と一緒に改めて出す。
- **骨組み**:判断のお願い(1点)/起きたこと/現在の状態/原因/調査のあとで出すもの/付録A 経緯
- **答える問い**:L2、L8、L14、S3、S5、反論2
- **元の決裁事項が倒れる問い**:S3(行29、行47)の答えで改修が原因でないと分かれば、行47のレビュー体制の強化は今回の障害と結びつかなくなる。L2(行31、行47)のとおり、行31は「判断できません」と書いている。S5(行45、行49)のとおり、確認の結果で中身が変わるなら、確認の前に3つの方向を了承してもらう理由が薄い。
- **縮めた決裁事項**:改修が原因かどうかの調査に1週間かけてよいか
- **弱点**:部長の了承を2回に分けることになる。監視のしきい値の見直しのように、調査の結果を待たなくてよい方向まで止める。
- **この案を選ぶなら先に見る問い**:S3(前日までに改修のほかに変わったものはあるか、半年前の通知と今回は同じ現象か)

## 案2 原因が未確定の報告として読み替える(選んだ案)

- **主張**:障害は復旧したが、メモリが上限に達した原因は確定していない。再発防止の3つの方向の了承と、改修が原因かどうかの調査に1週間かけることを決めてほしい。防止策の中身は調査の結果が出てから出す。
- **骨組み**:判断のお願い/起きたこと/現在の状態/原因/再発防止の方向/付録A 経緯
- **答える問い**:L1、L2、L3、L9、L14、S1、S2、S5、反論2
- **弱点**:調査と「改修のメモリ使用量の確認」が同じものか文書から言い切れず、了承を頼む2つが一部重なって見えるおそれがある。

doc.md の「経緯→原因→影響→対策」という時系列の枠を捨て、読む人が決める順に並べ替える。経緯の表と50分、約45分の時間は付録に回す。

## 案3 影響の大きさから始める

- **主張**:約300件のうち約40件が入力に失敗し、顧客に再入力の手間をかけた。現在は再発していないが、原因は確定していないので、2つのことを決めてほしい。
- **骨組み**:影響/復旧と現在の状態/原因/判断のお願い/再発防止の方向/付録A 経緯
- **答える問い**:L1、L9、S1、S2
- **弱点**:背骨に置く件数に、数え方の問いが多く残っている(L4、L12、L13、L15、S4)。営業本部長には響くが、情報システム部長が決める調査の話が後ろに下がる。

## 選んだ案と理由

案2を選ぶ。頼む中身を保つ案のうち、決めてもらう2つが最も早く読め、L2(判断できないものを策と呼ぶ)と L14(調査と対策が同列)に、並べ方そのもので答えられる。案3は背骨の件数がまだ確かめられていない。案1は書き手にしか選べないので、本文には使っていない。
