# 受注管理システム障害報告書(10月21日発生分)

宛先:情報システム部長、営業本部長
作成:情報システム部 運用チーム

## 了承をお願いしたいこと

了承をお願いしたいのは、再発防止の3つの方向と、受注検索の改修が原因かどうかの調査に1週間かけることの2つです。防止策の中身、担当、期限は、調査の結果が出てから改めて出します。

## いまの状態

10月21日(火)の午前中、受注管理システムの Web 画面が1時間半ほど応答しなくなり、11:50 ごろに復旧しました。疑っている受注検索の改修は切り戻しておらず、本番に残っています。再起動後はメモリ使用量を1時間ごとに見ていて、10月28日の時点で再発はありません。

## 原因

直接の原因は、処理を動かすアプリケーションサーバーのメモリが上限に達したことと見ています。調査でこの状態を確認し、再起動のあとに復旧しました。

上限に達した理由はまだ確定していません。前日の夕方に本番へ反映した受注検索の改修を疑っていますが、根拠は反映と障害の時期が近いことだけで、改修がメモリの使用量を増やしたことはまだ確かめていません。

レビューの体制が障害につながったかどうかは、改修が原因かが分かるまで判断できません。

## 影響

この時間帯に営業が入力した注文約300件のうち約40件、約13%が入力に失敗しました。残りの約260件は入力できているので、止まり方が全面的だったのか断続的だったのかは確認中です。

失敗した分は、営業が電話で顧客に再入力を頼み、10月22日までに全件入力し直しました。納期の遅れが出ていないことは営業本部に確認しました。顧客からの問い合わせはありませんでしたが、約40件の分は顧客に再入力の手間をかけています。

## 再発防止策

次の3つの方向の了承をお願いします。いずれも検討中です。

| 再発防止策 | 今回の障害との関係 |
|---|---|
| 改修のメモリ使用量の確認 | 受注検索の改修がメモリ上限到達の原因かどうかを判断する材料になる |
| 監視の通知を出すしきい値の見直し | 今回、運用チームが調べ始めたきっかけは 10:15 の通知だった |
| レビュー体制の強化 | 今回の改修のレビューは1人で行った |

1つ目の確認は原因かどうかを判断する調査で、1週間かけることの了承もお願いします。検証環境で改修の前後のメモリ使用量を比べる予定で、まだ始めていません。1週間あればできる見込みです。結果によっては、ほかの2つの策の中身も変わることがあります。

## 経緯

| 日時 | 出来事 |

通知から再起動までに50分、再起動から復旧までに約45分かかりました。
