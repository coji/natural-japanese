# 確認事項:受注管理システム障害報告書

## 出す前にやること

1. 再起動後のメモリ使用量の数値と推移を調べる。運用チームが1時間ごとに見てきた記録を見る → 概要の「再起動後はメモリ使用量を1時間ごとに見ていて、10月28日の時点で再発はありません」のあとに、数値と推移を1文で足す
2. 止まり方が全面的だったのか断続的だったのかを調べる。入力の成功と失敗の時刻が分かる記録を見る → 概要の「止まり方が全面的だったのか断続的だったのかは確認中です」を分かった止まり方に置き換え、同じ段落の前にある「Web 画面が1時間半ほど応答しなくなりました」も、それに合う言い方にそろえる
3. この注文をふだんシステムに入力するのが営業か顧客かを営業本部に聞く → 営業なら、概要の「営業が電話で顧客に再入力を頼み」を、顧客に何を頼んだのかが分かる文に直す。顧客なら、概要の「営業が入力した注文」を顧客が入力した注文に直す

## 先に答える問い

1. 疑っている改修を切り戻さず、本番に残している理由は何ですか。切り戻す、元に戻すといった案と比べましたか。読み手は「調査の1週間に再発したらどうするのか」も聞きそうです
2. 障害の前に入った変更や負荷の変化で、改修のほかに調べたものはありますか。改修を本番に残したまま10月28日の時点で再発がないことは、時期が近いことだけを根拠に改修を疑う見方と、どう関係しますか
3. 改修のメモリ使用量の確認は、了承を待たずに手元の記録で済ませられませんか。改修前後のメモリ使用量を比べられる記録があるなら、調査に1週間の了承をもらう必要があるかが変わります

## そのほか

- 「1時間半ほど」の起点はいつで、何で確かめましたか。本文の時刻で合うのは 10:15 の通知から 11:50 の復旧までの95分だけで、応答しなくなった時刻は文書にありません。営業の画面が止まり始めたのは通知より前ではありませんか
- 再起動の 11:05 から復旧の 11:50 までの約45分に何が起きていましたか。メモリの上限到達が応答停止を起こしたこと、再起動で復旧したことは、何から言えますか
- 通知から再起動までの50分と、再起動から復旧までの約45分の内訳は何ですか。3つの方向はどれも復旧までの時間を対象にしていません。同じことが起きたとき、また95分かかる見込みですか
- 約300件は、どの時刻からどの時刻までの注文を数えたものですか。影響の「この時間帯」は「1時間半ほど」と同じ起点ですか。約300件と約40件は、どの記録から数えた数ですか
- 監視の通知を出すしきい値の見直しについて、通知の基準のどこが今回問題だったのですか
- レビュー体制の強化について、レビューは本来何人で行うものですか。何と比べて強化が要ると言えますか
- 調査の結果、レビューの体制が障害につながっていなかった場合、レビュー体制の強化は方向として残しますか、外しますか
- 改修のメモリ使用量が増えていなかった場合、次に何を調べますか
- 調査の1週間はいつ始まり、結果はいつ出ますか。防止策の中身、担当、期限を「改めて出す」のはいつですか
- 再発防止の3つの方向のほかに、何もしない、範囲を絞る、といった案と比べましたか
- 改修を作り、レビューしたのは誰ですか。運用チームと同じ部門なら、レビュー体制の評価を当事者が行うことになり、別の部門なら、その部門が文書に出てきません
- 顧客からの問い合わせがなかったことは、影響が小さかったことを示しますか。顧客が営業の依頼に従っただけで、負担が表に出ていないとも読めます
